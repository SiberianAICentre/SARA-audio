# Архитектура SARA-audio

## Назначение системы

SARA-audio принимает один аудиофайл или каталог записей и преобразует их в
воспроизводимый набор артефактов: нормализованное аудио оператора, расшифровку,
признаки, диагностические данные и прогнозы MIC. Одинаковое ядро используется
CLI, web-интерфейсом и серверной smoke-проверкой.

## Контекстная схема

```text
Пользователь / интеграция
        |
        +-- sara-web ----------- Gradio UI, ZIP и preview
        +-- sara-extract ------- CLI одного файла или каталога
        +-- sara-server-smoke -- приемочная проверка GPU и артефактов
                    |
                    v
              BatchProcessor
                    |
         +----------+-----------+
         |                      |
         v                      v
   FeaturePipeline       ArtifactWriter
         |                      |
         v                      v
 audio -> VAD -> ASR -> признаки -> CSV/JSON/Parquet/WAV
                              |
                              v
                  MethodologyModelBundle
                              |
                              v
          filter -> 8 experts -> sex -> burnout
```

## Компоненты

### Точки входа

- `src/sara_audio/cli.py` содержит команды извлечения, проверки ASR, подготовки
  корпуса, smoke-теста и упаковки server delivery.
- `src/sara_audio/webapp.py` создает Gradio-интерфейс, ведет журнал web-сервера,
  сериализует GPU-задания и собирает ZIP.
- `src/sara_audio/web_worker.py` выполняет одно web-задание в отдельном процессе.
  Это изолирует web-сервер от native access violation в CTranslate2, PyTorch,
  ONNX Runtime или openSMILE. На Windows worker завершает процесс через
  `os._exit`, когда файлы уже записаны, чтобы не падать при уничтожении native
  объектов во время штатного завершения Python.

### Оркестрация батча

`src/sara_audio/runner.py` реализует `BatchProcessor`:

1. рекурсивно находит поддерживаемые аудиофайлы;
2. создает неизменяемый manifest входа и партии не больше `batch_size`;
3. запускает `FeaturePipeline` для каждой записи;
4. сохраняет детальные артефакты записи;
5. формирует общую широкую таблицу признаков;
6. запускает обычный фильтр или полный каскад методологии;
7. записывает `run_summary.json` только после успешного окончания.

Выходной каталог должен отсутствовать до запуска. Это защищает предыдущий
результат от частичного перезаписывания.

### Ядро обработки

`src/sara_audio/pipeline.py` координирует последовательность стадий:

1. `audio.py`: проверка WAV или конвертация через ffmpeg; выбор канала оператора;
2. `vad.py`: энергетический VAD, интервалы речи, внутренние паузы и длительности;
3. `audio.py`: сборка WAV только с речевыми интервалами;
4. `asr.py`: faster-whisper и временные метки слов;
5. `opensmile_extractor.py`: кадры ComParE 2016 и агрегаты;
6. `asr_features.py`: статистики слов, пауз и темпа по ASR-токенам;
7. `speech_rate.py`: скорости относительно активной речи VAD;
8. `mic_features.py`: скалярные признаки с именами, ожидаемыми JSON MIC;
9. `text_embeddings.py`: 1024 компоненты RoSBERTa `bert_1..bert_1024`;
10. `linguistic.py`: 92 лингвистических признака из версионированного реестра.

Стадии возвращают типизированные значения из `domain.py`. Интерфейсы
транскрибатора и экстракторов находятся в `interfaces.py`; тяжелые зависимости
импортируются лениво, поэтому базовый пакет и тесты не требуют GPU.

### Модели и прогнозы

`src/sara_audio/predictions.py` содержит:

- `JsonLinearModel`, загрузчик линейной модели из JSON;
- `MethodologyModelBundle`, набор из 11 обязательных моделей;
- нормализацию названия файла и вычисление группы оператор-год;
- полный каскад фильтра, восьми экспертных признаков, пола и выгорания;
- отдельный аудит пропущенных признаков для каждой модели.

`models/methodology/` является рабочим источником моделей. `meth_patch/` хранит
исходную передачу методологов и не читается production-кодом.

### Вывод и доставка

- `output.py` пишет CSV с разделителем `;`, JSON/JSONL и Parquet.
- `server_delivery.py` формирует компактные таблицы, XLSX, provenance manifest,
  SHA-256 и ZIP без повторной обработки аудио.
- `feature_filter.py` применяет `exclude_features.txt` к широким таблицам и
  delivery. Детальные артефакты записи при этом сохраняются.
- `external_delivery.py` импортирует ранее размеченный корпус без запуска ASR.

## Потоки выполнения

### CLI

`sara-extract` работает в одном Python-процессе. Это удобно для Linux, CPU и
отладки, но на проверенном Windows CUDA сервере предпочтительнее worker-команда
или web-интерфейс из-за особенностей завершения native библиотек.

### Web

Одно нажатие в UI создает `job-<id>`, копирует входные файлы в временные
подкаталоги, берет глобальную блокировку GPU и запускает:

```text
python -u -X faulthandler -m sara_audio.web_worker
```

Stdout и stderr worker-процесса пишутся в `processing.log`. После успеха web
читает `run_summary.json`, строит delivery при необходимости, читает preview из
`predictions.csv` и упаковывает весь job. При ошибке частичные файлы остаются,
а traceback web-уровня пишется в `error.txt` и `sara-web.log`.

### Docker

Контейнер использует тот же `sara-web`. CUDA runtime выбирается Dockerfile на
этапе сборки. Код, конфигурации и локальные MIC JSON входят в образ; вход,
результаты и кэш Hugging Face подключаются томами.

## Границы ответственности

- Конфигурация управляет техникой извлечения, но не изменяет коэффициенты.
- JSON моделей управляют уравнениями, но не содержат preprocessing/scaler.
- `BatchProcessor` отвечает за файловую транзакцию и порядок стадий.
- `FeaturePipeline` не знает о web, ZIP или grouping методологии.
- Web не вычисляет прогноз самостоятельно, а только отображает записанную
  таблицу.

## Расширение системы

Новый признак следует добавить через отдельный extractor, возвращающий
`FeatureValue`, зарегистрировать его в pipeline и добавить определение в
`src/sara_audio/data/linguistic_features.json`, если это лингвистический код.

Новый формат модели требует отдельного загрузчика. Нельзя молча менять смысл
существующего JSON, потому что текущий контракт равен `Intercept + sum(x_i*b_i)`.

Новый transport, например REST API или очередь, должен вызывать
`web_worker`/`BatchProcessor` и не дублировать pipeline. Для параллельных GPU
заданий нужен внешний scheduler и отдельный контроль VRAM; текущий web-сервис
намеренно обрабатывает задания последовательно.
