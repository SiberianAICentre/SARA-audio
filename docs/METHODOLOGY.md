# MIC: модели и прогноз

## Источники

- `models/methodology/` содержит канонический runtime-набор.
- `meth_patch/` содержит исходные файлы и код, переданные методологами. Этот
  каталог нужен для аудита происхождения, но production pipeline его не читает.
- `src/sara_audio/predictions.py` является исполняемой реализацией контракта.

При обновлении методологии сначала сравнивают новый handoff с `meth_patch/`,
затем осознанно заменяют канонические JSON и тестовые ожидания.

## Формат JSON

Каждый JSON является объектом `имя признака -> коэффициент`. Обязательный ключ
`Intercept` задает свободный член. Предсказание вычисляется так:

```text
score = Intercept + sum(row[feature] * coefficient[feature])
```

Это линейный score, а не вероятность, если методологи отдельно не гарантируют
обратное. Pipeline не применяет sigmoid, softmax или clipping.

В JSON нет `mean`, `scale`, `standard_deviation` или другого описания scaler.
Поэтому текущая реализация применяет коэффициенты к исходным значениям колонок.
Фраза о прогнозе по стандартизированным показателям не может быть восстановлена
из этих файлов автоматически. До появления scaler-артефакта стандартализацию
нельзя добавлять предположением.

## Порядок каскада

### 1. Фильтрация записи

Для каждой записи вычисляется `filter_score`. Сравнение соответствует исходной
реализации методологов:

```text
accepted = round(filter_score, 8) < filter_threshold
```

При стандартном пороге `0.5` запись со score ровно `0.5` исключается. Все строки,
включая исключенные, остаются в `filter_predictions.*` для аудита.

### 2. Реконструкция экспертных признаков

Только для принятой записи вычисляются восемь экспертных score. Они не
бинаризуются и добавляются к полной строке признаков.

### 3. Группировка оператор-год

Имя исходного файла используется как идентификатор наблюдения. Pipeline
извлекает год из первых четырех цифр timestamp и имя/номер оператора из
оставшейся части. Префиксы `Agent`, `Operator` и `Оператор` нормализуются.

Пример:

```text
20230904103009_Agent_12.wav -> группа agent_12 / 2023
```

Если имя не соответствует ожидаемому шаблону, группа равна `uploaded_batch`.
Это безопасный технический fallback только для smoke-test. В production он
может объединить записи разных людей, поэтому входные имена должны быть
нормализованы до загрузки.

Для каждой группы берется среднее всех числовых признаков принятых записей.

### 4. Пол

`agent_sex.json` применяется к средней строке группы. Бинаризация:

```text
is_male = round(agent_sex_score, 8) > 0.5
m = 1 if is_male else 0
f = 0 if is_male else 1
```

Значение `0.5` относится к `f`. Бинарные `m` и `f` добавляются и в среднюю
строку, и в строки записей, поскольку они нужны итоговой модели.

### 5. Выгорание

`burnout.json` применяется к обогащенной средней строке группы. Полученный
`burnout` присваивается всем принятым записям этой группы. Итог:

```text
burnout_final = int(round(burnout, 8) > 0.5)
```

`burnout_final=1` означает положительный класс модели, `0` отрицательный.
Сервис не называет класс клиническим диагнозом.

## Что получает пользователь

`predictions.csv/json` содержит компактный результат:

- `file_id`, `file_name`: внутренний id и исходное имя файла;
- `agent_year_id`: вычисленная группа;
- `burnout`: линейный score до бинаризации;
- `burnout_final`, `burnout_label`: класс `0/1` и метка `Нет/Да`;
- `agent_sex_score`: score модели пола;
- `agent_sex`, `agent_sex_label`: бинарный класс `0/1` и метка `F/M`;
- `filter_score`: score входного фильтра;
- `group_input_count`: число всех записей группы;
- `group_informative_count`: число записей группы после фильтра.

`interpretation_input.csv/json` содержит те же идентификаторы, все исходные
признаки, восемь реконструированных expert features, пол и выгорание. Это вход
для будущего отдельного блока интерпретации. Интерпретация намеренно не встроена
в MIC-модуль.

## Пропущенные признаки

Загрузчик модели различает отсутствующий признак и значение `0`. Отсутствующие
колонки не участвуют в сумме и перечисляются в диагностике модели. Это позволяет
отлаживать несовпадение версии extractor и коэффициентов, но не доказывает
корректность score. Для production отсутствие признаков модели следует считать
ошибкой данных и расследовать по `interpretation_input` и логам.

## Приемка новой версии моделей

1. Получить JSON, исходный код/ноутбук, описание preprocessing и порогов.
2. Проверить наличие `Intercept` и числовые значения всех коэффициентов.
3. Зафиксировать, исходные или стандартизированные признаки ожидает модель.
4. Если нужна стандартизация, получить отдельные mean/scale для каждого поля.
5. Сверить имена коэффициентов с колонками `features_wide.csv`.
6. Запустить golden sample в коде методологов и SARA, сравнить каждый этап.
7. Обновить `tests/test_methodology_predictions.py` и эту документацию.
8. Выполнить smoke-test на реальном аудио и сохранить артефакты релиза.

## Известные методологические вопросы

- Кто и на каком наборе определил порог `0.5` для filter/sex/burnout.
- Являются ли линейные score вероятностями или только ranking score.
- Где находится scaler, если обучение велось на стандартизированных признаках.
- Как должен формироваться operator/year id для файлов без timestamp.
- Как интерпретировать результат, если часть записей группы удалена фильтром.

Эти вопросы не блокируют техническое выполнение, но блокируют утверждение
семантической эквивалентности исходной обучающей процедуре.
